# Teórica 06

**¿Qué problema resuelve `Optional`? Compará `orElse`, `orElseThrow` y `map` sobre un Optional.**

El problema es el `null` como respuesta a "no encontré". Un método que devuelve `Alumno` puede devolver `null`, y NADA en su firma lo avisa: el que llama se olvida de chequear, y el `NullPointerException` explota lejos, en otro método, otro día. `Optional<Alumno>` mete la posibilidad de ausencia EN EL TIPO: el que llama no puede ignorarla, porque para sacar el valor tiene que decidir explícitamente qué hacer si no está.

Las tres aperturas, y cuándo usar cada una:

- **`orElse(valorPorDefecto)`**: "si no está, usá esto". Para ausencias NORMALES con un default razonable: `promedio().orElse(0.0)`, `buscar(nombre).orElse(ALUMNO_ANONIMO)`.
- **`orElseThrow(() -> new NoSuchElementException(...))`**: "si no está, es un error del que llama". Para ausencias que violan una precondición: si el flujo ya garantizaba que el alumno existe, que explote acá, con un mensaje claro, y no tres métodos más adelante.
- **`map(funcion)`**: transformar el valor SI está, sin abrir el Optional: `buscar(nombre).map(Alumno::nota)` da un `Optional<Integer>` — vacío si el alumno no estaba. Encadena la ausencia sin un solo `if`.

El antipatrón: `optional.get()` sin chequear — es el `null` con sombrero, revive exactamente el problema que Optional vino a matar. Y su primo: `if (opt.isPresent()) { opt.get() }`, que funciona pero ignora las herramientas — casi siempre hay un `orElse`/`map`/`ifPresent` más claro.
